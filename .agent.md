# SMS v3 Agent

Use this agent for real bug-fix work in this repository. Its job is to find and fix runtime problems that affect actual app behavior for logged-in users, not merely to make the build green.

## When to use this agent

Pick this agent when a task involves:
- a page or feature that is broken in the browser
- RBAC or permission-gating issues
- Firestore data loading, shape mismatches, or missing-state bugs
- auth-related runtime problems
- regressions that are not visible from a successful build

## Core mission

Treat every task as:
- Does this page actually do what it is supposed to do for a real user?
- Does the behavior match the documented app flow and role expectations?

## Before touching code

1. Run the project setup steps if needed:
   - npm install
   - npm run build
2. Read the project docs first:
   - docs/ARCHITECTURE.md
   - docs/RBAC.md
   - docs/TROUBLESHOOTING.md
3. Reproduce the bug or understand the reported symptom before changing code.
4. If possible, run the app and exercise the affected flow in a browser.

## Important repository context

Prefer these locations first when investigating a problem:

- Routing and app providers: src/App.jsx, src/main.jsx
- Auth state: src/contexts/AuthContext.jsx
- Role constants: src/config/rbac.js
- Permission mappings: src/config/permissions.js
- Firestore access layer: src/services/api.js
- Route guards: ProtectedRoute, PermissionGate
- Seed/demo data: seedData.mjs

## Working rules

- Keep Firestore access centralized in src/services/api.js.
- Do not add direct Firestore calls from components unless the task explicitly requires a new helper in the API layer.
- Preserve existing RBAC behavior unless the task is specifically about permissions.
- Do not modify serviceAccountKey.json.
- Avoid changing unrelated code just to make a symptom disappear.
- Prefer small, targeted fixes that address the root cause.

## Debugging approach

When a runtime bug is reported, investigate in this order:

1. Confirm the symptom and reproduce it.
2. Check the relevant docs and existing implementation patterns.
3. Compare the permission key used in the UI against the mapping in src/config/permissions.js.
4. Verify the expected Firestore document shape against what the page reads.
5. Look for missing loading states or unguarded property access.
6. Check for Firestore permission errors or data-shape mismatches.

## Baseline checks

If you are auditing or validating this app, re-run checks such as:

```bash
node --check seedData.mjs
grep -rn "role\s*===\s*['\"]" src/ | grep -v '\.bak'
grep -rln "collection(" src/ | grep -v "src/services/api.js"
npm run build
```

## Stale files

If the repository still contains these files and they are confirmed unused, remove them:
- src/App.jsx.bak
- src/pages/Results.jsx.bak

Do not "fix" them in place; delete them after confirming they are unused.

## Definition of done

A fix is complete when:
- npm run build still succeeds
- the reported symptom is gone
- the affected flow was verified in the app or through a concrete reproduction step
- no new console errors were introduced for the affected page/flow
- RBAC behavior remains intact unless explicitly changed
